### 1.4 额外的隔离审查探针

使用本地依赖中的 sqlite-jdbc 3.46.1.0 源码及临时 SQLite 文件核验事务行为；没有新增或修改项目测试文件。临时文件在连接关闭后删除。

1. 驱动默认事务模式为 DEFERRED。连接 A 调用 setAutoCommit(false) 后、尚未读写时，连接 B 仍能成功写入。显式 IMMEDIATE 模式下同样的 B 写入返回 SQLITE_BUSY。现有 helper 不等于 BEGIN IMMEDIATE。
2. 在 SqliteTransactions.run 内调用现有 ExecutionRepository.load，确实抛 CommitOutcomeUnknownException，信息为“SQLite transaction is unresolved; committed production facts cannot be confirmed”。
3. 注入“业务写入后失败 + rollback 在实际回滚前抛异常”，现有 helper 返回 CommitOutcomeUnknownException，但另一连接读到已提交行数为 1，连接恢复到 autoCommit=true。原因是 finally 中 setAutoCommit(true) 提交了仍在进行的事务。这是已复现的事务清理缺陷，不只是理论风险。

### 2.1 当前调用关系

    NeoForge ServerTickEvent.Post
      -> ServerEconomyRuntime / ServerEconomyContext
      -> EconomicClock
      -> ProductionService
          -> PM Repository / Execution Repository
          -> ProductionInventoryPort -> SqliteInventoryStore -> GoodsInventory
          -> ProductionEquipmentService -> EquipmentHolding / Registry / SQLite
          -> WorkforcePort -> EmploymentService -> EmploymentRegistry / SQLite
          -> BuildingPayrollPort（正式服默认 UNAVAILABLE）

    EmploymentService / EquipmentService
      -> RepositoryProductionFacts
      -> PM / Execution Repository（反向获取容量、参产保护和边界授权）

ProductionBuildingInitializer 使用共享连接事务初始化 Building、PM、Execution 三条根记录。之后各自独立持久化。Inventory 地点由调试命令另行创建，尚不属于这一原子初始化。

production/domain 依赖 common/definition；production/application 直接依赖 inventory/application。inventory/infrastructure 依赖 production/port 的库存契约；production/infrastructure 又实现 inventory/port 和 workforce/employment 的保护端口。包间存在双向协作，需要谨慎拆除，不能按包名整包删掉。

### 5.2 共享事务的必要改动

- 一个连接、一个世界经济锁目前能串行化 Context 内调用，但不能约束另一连接。招聘、减供给、资金预留、付款必须在取到写权限后重读相关权威，再判断约束。
- 两个生产仓储的 public load 均调用 requireCommittedReads。必须保留“恢复查询不能把未提交值当事实”的保护，另加只允许显式 UoW 使用的事务内加载接口；不能简单删 guard。
- 当前 ExecutionRepository.save 在内层 savepoint release 后就 acknowledgeCommit。若外层随后回滚，对象 revision 已前进。新流程应延迟发布至外层成功，或严格丢弃整个事务内对象图，不把它放进 Registry。
- rollback 失败后必须隔离/关闭不可信连接，不能 finally 一律 setAutoCommit(true)。未知提交保留操作标识，使用可信连接核验；禁止推断“异常就是没提交”。
- 驱动 commit/rollback 会按连接配置立即开始下一事务；写 UoW 的实现需同时验证 JDBC 状态与 SQLite 锁，避免手写 BEGIN 与 JDBC 再次 BEGIN，或让所有只读仓储都无谓获取 IMMEDIATE 写锁。
- Inventory 应把 load-domain-mutate-save 放在同一写 UoW 并加地点 revision CAS；单条 UPDATE 原子不等于整个读改写原子。保留数量与回执一体提交即可，不强制本轮归一化全部库存表。

### 5.3 必须保留的启动和结算恢复

现有顺序为：StartIntent 持久化 -> 全额预留 -> 设备保护 -> 最终复核 -> Execution+Batch 原子提交 -> 删除 StartIntent。

- Batch 未提交且已确认：按同一 BatchId 幂等 release，成功才删意图。
- Batch 已提交：保留它的预留，不得补偿；只清理意图。
- Batch 是否提交无法确认：保留意图和资源，阻止新开工，等待可信事实。
- release 失败：持久意图保留，重启继续重试。
- 结算：先持久 SETTLING 状态；Inventory 一次性保存数量变化/释放/回执；再确认 Execution。回执丢失时按 BatchId 和同一冻结命令核对，不能重复产出。

取消设备后只删除上面的设备保护步骤，Reservation、StartIntent、Journal 的其余责任仍然成立。若未来把预留与 Batch 开始也合入一个物理事务，须先用相同故障矩阵证明等价，再讨论精简；本计划不以删 Journal 为目标。

设计草案中的 settleCompleted(building,batch) 签名只是草图：当前 Inventory 仅知道预留输入，不知道冻结输出配方。建议传不可变结算命令，明确 COMPLETED/ABORTED、输入/输出及承诺指纹；回执记录结果类型与匹配依据，避免靠 double progress 推断，也避免中止的零数额掩盖冲突请求。

## 6. DDD 方案审查结论

### 6.1 保持 Production 双聚合

合理，且是已确认约束。PM 保存有效/待生效配置；Execution 保存批次生命周期与开工屏障，Batch 不单独增加 Repository。运行时 tick 不应每次改写 PM；运行中提交 Pending 也不应必须保存 Execution。

独立聚合不意味着禁止应用事务跨根提交。PM“请求 Pending”和“真正生效”必须区分：前者可以独立 CAS，后者与 Staffing、工资截止和屏障同事务。现有“PM 已生效但人员协调失败”的测试行为必须改掉。

methods_effective_revision 当前有真实用途：证明旧独立 PM 生效后已经走过人员协调。只有所有生效入口都进入新原子 UoW、无旁路后才可删除；新的屏障加版本约束若足够，就不再保存这个冗余检查点。Batch 的 effectiveRevision 作为历史快照仍应保留。

### 6.2 BuildingStaffing 独立根

合理。人数/Pending 不应回塞 EconomicBuilding，也不归 Execution。Staffing 不存 region available，不复制岗位权威；岗位上限来自同事务读取的有效 PM。

其内部约束：非负、每职业一目标、缺失与 0 区别、revision。跨根约束：人数 <= 当前 PM 需求、区域 SUM(employed) <= supply、变更前先应计工资、生命周期准入。应用服务/UoW 承接跨根约束，不能假装只靠 aggregate.apply 就能保护。

一次部分招聘成功后消耗这次 Pending，记录/返回实际结果；不能把剩余差额留成下一 tick 自动补招。拒绝或未知提交则不能把请求误标为已消费。

### 6.3 单一重配置屏障

可替代旧三阶段，但有明确前提：设备彻底退出；不再有异步 NPC 转岗/同意流程；PM+Staffing+工资截止+Execution 在一个物理事务内完成。

可靠流程：

    SETTLING_* 持久决定
      -> Inventory 对同一 BatchId 幂等完成/中止
      -> 已终结 Batch + RECONFIGURING 持久保存
      -> 写 UoW 中读最新身份/PM/Staffing/供给/工资/Execution
      -> 旧人数计薪；PM 生效；自动裁员；Pending 收缩并执行一次
      -> 保存各根 revision；清屏障；外层提交
      -> 可开下一批，新批本 tick 不推进

失败不清屏障；提交未知先查已提交版本，不从内存继续。人工 start、自动 start、retry 和 startup 必须共用准入条件。

空闲 PM 立即生效也走同一事务；Payroll 不可用时，不能先落 PM 再忽略应计失败。仅仅保存运行中的 Pending 不必依赖库存、可支付现金或真实付款成功。

建议先让 RECONFIGURING 仍要求有一个已结束 current Batch，以保持当前 rehydrate 不变量；空闲 PM 修改直接原子处理。若另需空闲持久重配置意图，再显式扩展模型，不伪造一个 ended Batch。

### 6.4 Payroll 与 Company Finance

应计和付款分离合理。不能把工资挂在 Batch 上，不能因停产/库存满/auto=false 停止应计。

- 工资变更、人事变更、所有权切换先应计旧状态至生效 tick；同一事务再改权威状态。
- 以公司/币种为付款范围，先按建筑组汇总到期债务，再用精确整数最大余数法分配；BuildingId 使用稳定规范顺序。组内多历史段/地区的付款拆分还需要一个确定性规则。
- 扣公司可用现金、更新欠薪、加居民真实账户、付款 run/line 与账本同事务。可用现金扣除一切有效市场资金 Reservation。
- 每周期至多一次“已完成付款”，即使支付为 0，也要明确定义周期尝试已经完成的事实；失败回滚/未知核验不能被当作第二次付款。
- 可采用 UNIQUE(company,currency,period) 加公司周期父记录；若坚持 UNIQUE(company,period)，一次 run 必须同时封装其各币种分区。不可由几个独立币种服务绕过“公司每周期一次”的已确认规则；也不引入换汇。
- AccrualBucket、Liability 可以是同一 Payroll 仓储内分开的实体/表，不必各有通用 CRUD 接口。PaymentLine 不应成为另一个可以任意更新的根。
- HouseholdBudget 只保存用途额度，现金以 FinanceAccount 为唯一权威；不能把储蓄和消费做成两份真实余额再重复加工资。

### 6.5 避免过度设计与重复权威

不引入地区 occupied/available 可写余额、Building 内人数镜像、第二份 Effective PM、生产内工资余额、Budget 内现金镜像、虚拟 NPC，以及专用设备替代物。

保留已有可用的根、计算器和异常。新增端口围绕真实外部上下文或 UoW，不为每个实体建接口。生命周期用一份最小操作记录即可，不需要通用 Saga 平台、消息中间件或事件溯源改造。

必须保住的现有不变量：Batch 单建筑排他、冻结快照不变、进度不回退、终止不可逆、SETTLING 不被覆盖、开始不留下无主预留、结算不重复、普通出库不能动预留、已承诺产出允许首次超容但阻止新开工、恢复查询不信未提交值、Building 写入不覆盖独立生产状态。

被正式新规则替代的旧不变量：NPC 单任职/资格/参产保护、设备总容量/安装锁定/边界授权、比例终止、1200 tick 满速、无职工产出配方。替代它们的是汇总人数唯一权威、地区稀缺供给、工资义务、人数冻结快照和单重配置事务；删除旧保护必须与替代能力接上。

以下草案未决保持未决：

1. 出售时 Pending PM 继承/取消/复核。
2. 出售/拆除后的不足最小货币单位余数如何在原公司精确清算；必须保留，不能转给买家或丢弃。
3. 库存资产是否随建筑出售、退料回到谁的资产范围。
4. 多币种及居民账户接口；不引入汇率和跨币种付款。
5. 当前有效 v2 世界到下一版的兼容策略；本地找到空的 v1 文件不改变这个问题。
6. 生命周期意图的最终存档位置。本报告建议最小操作表，但没有把它提升为已确认需求。

另需在对应工作包开始前补齐的输入：

- 公司/地区初始身份、地区平均工资值/币种、初始劳动力供给、真实初始现金来源。不能通过调试初始化随意造钱来闭环。
- pig_iron_tools 的正式职业需求；仅确定“零职业产出必须拒绝”，不擅自确定岗位数。
- 同一建筑组内多债务段/受益地区如何确定性拆分付款行；最大余数法在“建筑之间”已确认，段内规则尚不充分。
- 运行状态 STOPPED/DISABLED 与新的生命周期、其他暂停原因如何映射；现有 stopBuilding 只挡新开工，已运行批次仍会推进，不能默默改为中止。
- 服务器运行时异常的持久经济 tick 与工资游标恢复策略：持久序号不能重复或倒退，事务失败不能丢失已发生的工资时段。这是实现一致性设计，需在时钟工作包给出可验证协议。

这些输入不妨碍先做事务基础工作；涉及未决规则的实现留在对应门槛之后。

## 8. 分阶段实施计划

### 8.1 实施原则与顺序

M0 本轮完成到此；下面每个工作包都应独立构建和测试，规模过大时再在同一不变量边界内拆提交。没有任何工作包已经获准开始。

每包通用验收：相关 JUnit/SQLite 故障测试通过，再执行完整 test/build；没有未解释的失败或跳过；实际世界文件不变；没有对远程写入。行为变化的旧测试必须改写成新需求，不能以删除失败断言作为验收。

Schema/序列化改变必须在兼容策略确定后进入正式装配。各开发工作包可用独立临时数据库验证；不可给同一 schema version 赋予几种不兼容布局。中间布局若需要落盘，必须各自明确版本/能力标识；最终版本号由兼容方案确定，不提前把所有包都宣称为“v3 迁移”。

建议依赖顺序：

    M0
      -> M1.0 失败清理
      -> M1.1 UoW
      -> M1.2 兼容/编解码门槛
      -> M1.3 整数批次
      -> M1.4 设备退出
      -> M2.1 身份及人数持久化
      -> M2.2 Staffing 命令/查询准备
      -> M4.0 持久时钟
      -> M4.1 真实账户与预留
      -> M4.2 真实应计和欠薪事实
      -> M3.1 汇总雇佣切换及单屏障原子边界
      -> M3.2 tick / 暂停恢复
      -> M4.3 公司统一付款与居民到账
      -> M4.4 居民预算
      -> M5.1 出售
      -> M5.2 拆除
      -> M5.3 收尾与游戏验收

M4 的基础部分提前，是草案实施顺序的必要优化：新雇佣一旦真实生效，就必须有真实公司/地区归属及变更前工资应计，不能等到 M4 最后才补历史。M2.1/M2.2 可以独立完成领域及持久化测试，但不向正式服开放新的雇佣写入口。M3.1 才做唯一权威切换，避免临时 UUID 适配器或双写就业人数。

### M1.0：事务失败清理，建议首先实施的最小工作包

1. **具体文件**：修改 S/storage/sqlite/SqliteTransactions.java；必要时只调整同目录 CommitOutcomeUnknownException.java 的原因/连接状态表达；新增 T/server/storage/sqlite/SqliteTransactionsTest.java。复用 ProductionRepositoryTest 既有实际 JDBC 提交回执丢失场景。
2. **类处理**：保留 helper 和未知结果异常，不删除类，不加业务根，不变 Schema。
3. **不变量**：工作失败后不能由清理动作提交；rollback 失败后连接不得重新作为可信权威来源；已经提交但回执丢失不误判未提交。
4. **兼容风险**：现有调用者可能依赖 helper 最后把 autoCommit 恢复为 true；改为隔离失效连接后，Context 应停止该连接上的后续写入并保留恢复事实，不能吞异常继续运行。首包可明确以关闭/不可用作为安全结果。
5. **测试**：实际 JDBC 代理注入工作失败、rollback 前失败、commit 已生效后回执失败、清理失败、嵌套 savepoint 失败；检查失败工作绝不会因 finally 被提交。未知连接上不能直接开放恢复读取。
6. **验收**：本轮“工作失败+rollback 失败仍提交一行”的探针不再出现清理提交；旧的提交已成功但回执丢失仍能重读确认；94 项旧测试适用部分全部通过，完整 build 成功。
7. **前置依赖**：仅需用户审阅本报告并开始实施阶段；不需要先决定 PM 数据、工资值或世界迁移。

## 10. 本轮结论与下一步

双生产聚合与独立 Staffing 的方向合理；单屏障和共享写事务能简化旧边界，但现有仓储/连接清理尚不支持安全直接套用。最大的实施前置是事务基础、世界格式兼容以及真实公司/地区/时钟/工资应计。

建议首先只实施 M1.0：修复失败事务清理并增加针对性的 JDBC 故障回归。该包不涉及业务规则、Schema、世界迁移、设备或 NPC 删除，可单独审查和构建。随后做 M1.1，再开始整数批次与设备退出。

本轮仅交付审查与计划；没有修改业务源码、数据库 Schema 或项目测试，没有改写用户草案，没有改变世界数据库，也没有 Git 提交或推送。下一实施阶段等待用户审阅。
